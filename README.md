# docker-homer

A simple container image for Homer. It ships the static [Homer](https://github.com/bastienwirtz/homer) dashboard as a data-only image, published to `ghcr.io/trexx/docker-homer`, for a separate web server to serve.

## Overview

Serving [bastienwirtz/homer](https://github.com/bastienwirtz/homer) in a scratch image. Intended to be ran in a Kubernetes environment.  
Some resources pre-gzipped. Image Size ~1.07MB. Memory usage: ~304KB.

The [Dockerfile](Dockerfile) has two stages:

- `download-homer` (`bash:5.3`) downloads `homer.zip` for `HOMER_VERSION` (currently `v26.08.3`) from Homer's GitHub releases and unpacks it without `logo.png` and the `*.md` files. It removes everything in `assets/` except `icons` and `manifest.json`, compresses all `.html`, `.js`, `.css`, `.svg` and `.ico` files with `gzip -9` (only the `.gz` files are kept), and makes `assets/config.yml` a symlink to `/etc/homer/config.yml`.
- The final image is `FROM scratch` with the files at `/`. It holds only the site and runs nothing by itself.

## Usage

Images are published as `ghcr.io/trexx/docker-homer:<version>` and `ghcr.io/trexx/docker-homer:latest`. Release tags are Homer's version without the `v` and leading zeros: Homer `v26.08.3` is tagged `26.8.3`.

The artifact generated by this repo assumes the container image is mounted as an image-volume to a pod running a http webserver. For example:

```yaml
spec:
  containers:
    - name: homer
      image: ghcr.io/trexx/docker-busybox-httpd:1.37.1-1
      volumeMounts:
        - mountPath: /etc/homer/
          name: config
        - name: www
          mountPath: /www
      ports:
      - name: http
        containerPort: 8080
  volumes:
    - name: config
      configMap:
        name: config
    - name: www
      image:
        reference: ghcr.io/trexx/docker-homer:26.8.3
```

The web server needs to serve the pre-gzipped files, as [docker-busybox-httpd](https://github.com/trexx/docker-busybox-httpd) does for clients that accept gzip.

## Configuration

Homer reads `assets/config.yml`, which in this image is a symlink to `/etc/homer/config.yml`. Mount your Homer configuration there, for example from a ConfigMap at `/etc/homer/` as in the example above.

## Development

Build the image locally with:

```sh
docker build .
```

Dependency updates:

- [Renovate](.github/renovate.json) updates `HOMER_VERSION` from Homer's GitHub releases through the `# renovate: datasource=github-releases depName=bastienwirtz/homer` comment above it in the Dockerfile, and the `bash` base image.

Workflows in `.github/workflows`:

- `container-check.yml` runs hadolint on the Dockerfile and builds the image without pushing it, on pull requests and pushes to `main`.
- `trivy.yml` scans `ghcr.io/trexx/docker-homer:latest` daily and uploads the results to the repository's Security tab.

## Releases

Releases are cut with the Release button: Actions → Release → Run workflow ([`.github/workflows/release.yml`](.github/workflows/release.yml), which calls `trexx/actions`' `release-image.yml`). Run it from the default branch.

1. It works out the tag from `HOMER_VERSION` in the Dockerfile, without the `v` and leading zeros: `v26.08.3` becomes `26.8.3`. If that version was released before, it uses `<version>-N` for the rebuild (for example after a base image update). A tag can also be given by hand in the `tag` input.
2. It builds the image and pushes it as that tag and `latest`.
3. It creates the git tag and the GitHub release.

Ticking "dry run" only works out the tag and builds the image; nothing is pushed and no release is created. Old images are pruned from the package after a push (`latest` and the newest tagged images are kept).

Pushing a tag by hand (matching `*.*.*`) still works: [`.github/workflows/build.yml`](.github/workflows/build.yml) builds and pushes the image for that tag.
